NIKA GeoEngine, previously called NIKA Worker, is geoprocessing orchestration for your own Kubernetes cluster. Bring Python or R workers; NIKA GeoEngine runs them on the right machine, fans big jobs out in parallel, keeps sensitive analyses to cleared roles and measures every run.

<Note>
  **Two complementary products, one worker format.** [GeoEngine CLI](/nika-geoengine/overview) builds and tests workers on a laptop. NIKA GeoEngine runs the same workers at scale in your Kubernetes cluster.
</Note>

## Architecture at a glance

A **control plane** decides who may run what, where and when. An **execution plane** of pods does the work. Both run in your cluster, against storage you own.

| Component | Job |
|---|---|
| **Gateway** | Single entry point. Authenticates every caller. |
| **Access control** | Checks the caller's roles against the worker before anything is scheduled. |
| **Orchestrator** | Queues jobs, fans batches out into tasks, places each task on its pool, tracks state. |
| **Worker catalogue** | Every published worker version: preset, your own, and restricted. |
| **Observability** | Runtime and CPU, GPU and RAM use for every run. |
| **Pools and storage** | Your CPU, high-memory and GPU nodes, and the storage every task reads and writes. |

## Concepts

| Term | Meaning |
|---|---|
| **Worker** | One versioned, containerised processing unit, such as conversion, cloud removal or your own script. It declares typed inputs and outputs. |
| **Worker version** | A semantic version such as `1.2.0`. Immutable once published. Jobs name the exact version, so results stay reproducible. |
| **Job** | One request to run a worker version on some inputs, with an ID, an owner, a status and a resource record. |
| **Batch job and task** | A batch job covers many items, such as 200 scenes, and fans out into tasks: one pod per item. |
| **Machine class** | CPU, high-memory or GPU. Each class maps to a node pool in your cluster. |
| **Restricted worker** | A worker that only granted roles may run. Every other worker is open. |
| **Geo runtime** | The managed base under every worker: GDAL, PROJ, CUDA and the core geospatial libraries. |
| **Shared storage** | The volume or object store you own, where inputs are read and results are written. |

- **Access is checked before capacity is spent.** A denied request never creates a pod.
- **Tasks are independent.** One failed scene does not stop the others, and results are written per task.
- **Capacity is elastic but bounded** by the limits you set on each pool.

## Is it right for you?

<Columns cols={2}>
  <Card title="A good fit" icon="check">
    - Raster pipelines and imagery analysis
    - Jobs that need GPUs or more memory than general nodes have
    - Many scenes, same logic
    - Data that must stay in your cluster, with some analyses limited to certain roles
  </Card>
  <Card title="Probably not" icon="xmark">
    - One small script that runs fine on a laptop
    - General ETL or ML-lifecycle needs with no geoprocessing
    - No Kubernetes cluster to run it on
  </Card>
</Columns>
